深度头脑风暴：交互协议的多维度设计

已经聊了 View/Interaction/DSL/WASM，还有哪些维度需要探索？

维度 1：生命周期 — View 是"发出去就忘"还是"持续更新"？

A: 一次性 View

AgentResponse { views: [{...}], interaction: {...} } → 用户交互 → InteractionResponse → Agent 继续 → View 不再需要

简单，适合大多数场景。当前设计默认走这个。

B: 持续更新 View

AgentResponse { views: [{ id: "v1", ... }] } → View 在 UI 中持续展示 → Agent 后续发 ViewUpdate { id: "v1", data: {...} } → UI 原地更新，用户看到进展

适合：长时间分析、实时数据监控、多步处理逐步展示。

维度 2：View 嵌套与组合 — 多个 View 之间怎么关联？

A: 平铺列表

views: [table, chart, form]

从上到下渲染。简单，当前设计默认。

B: 标签页/分栏

views: [{ type: "tabs", tabs: [ {label:"数据", view: table}, {label:"图表", view: chart} ]}]

LLM 输出组合布局 DSL。

C: 级联关联

View A (表格) → 用户选择一行 → InteractionResponse { viewA: "row-3" } → Agent 产出 View B (该行详情)

交互结果影响后续 View，类似 drill-down。

维度 3：交互深度 — 一次 AgentResponse 支持多少轮对话？

单轮 (当前设计)

Agent → Interaction → 用户回应 → Agent 继续 ↑___________________________↓ 一次回应

多轮

Agent → Interaction → 用户回应 → Agent 临时处理 → 新的 Interaction → 用户再回应 → Agent 最终继续 ↑________________________________________________________↓ 多次回应

场景：分步向导、多步表单、逐渐深入的分析。

维度 4：视图状态 — 用户离开再回来还能看到吗？

无状态

View 只在当前对话中存在。刷新/重连后消失。

持久化

View 保存到 StateStore。重连后恢复。适合长时间后台任务的结果查看。

维度 5：多 Agent 协作的 View
Orchestrator 分析任务 → 分配子任务 ├─ Agent A (reasoning): 输出分析 View (表格/流程图) ├─ Agent B (codegen): 输出代码 View (diff) └─ Agent C (review): 输出审查 View (卡片列表) ↓ ChainTransferManager 收集所有 View → 合并展示给用户

问题：每个 Agent 的 View 是独立展示还是合并为一个 dashboard？
如果是 dashboard，需要 ViewFrame 类型——一个固定布局模板，Agent 填入内容。

维度 6：错误与恢复
场景问题处理
View data 校验失败LLM 输出的 DSL schema 不对重试 prompt "上次格式有误，请重新输出"
用户输入无效表单验证不通过Agent 收到 invalid 响应，重新输出 Interaction
View 渲染失败组件不支持某个 data降级为 markdown 文本展示原始 data
用户长时间不响应Interaction 超时Agent 自动继续（超时策略可配）
维度 7：扩展性 — 第三方如何加新 View 类型？

内置组件库

框架提供标准组件 (table/card/tabs/row)。LLM 只能选这些。

安全可控，LLM 输出质量高。

插件渲染器

第三方注册新的 ViewRenderer。提供 schema + description → 自动注入 prompt。

灵活，但需安全审查。

我的建议：按需渐进，不要一开始全做
Phase 1: 一次性 View + 平铺列表 + 单轮交互 + 无状态 + 内置组件 Phase 2: View 持续更新 + 标签页组合 + 持久化 Phase 3: 多轮交互 + 多 Agent 合并 + 插件渲染器

这些维度里，哪些觉得重要需要现在考虑？哪些先跳过？
